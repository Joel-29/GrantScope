# Permit2 AllowanceTransfer (Module 7)

The integration uses exact typed ABI entries from Uniswap's MIT-licensed [IAllowanceTransfer](https://github.com/Uniswap/permit2/blob/main/src/interfaces/IAllowanceTransfer.sol): `allowance`, `lockdown`, Permit, Approval, Lockdown and NonceInvalidation, plus relevant errors. This is a deliberately narrow ABI, not the separate SignatureTransfer ABI. The canonical `0x000000000022D473030F116dDEE9F6B43aC78BA3` address on Ethereum and Sepolia is referenced in the official [deployment table](https://developers.uniswap.org/docs/protocols/v3/deployments/v3-ethereum-deployments). Runtime checks verify the selected chain, nonempty deployed code and decodable state. The observed runtime code hash is retained with each grant; this is not an independent bytecode audit.

Known-pair inspection reads four registered token/spender pairs plus any explicit manual pairs. Event mode filters the canonical Permit2 emitter, indexed owner, and official Permit/Approval signatures in the latest 2,000 blocks ending 12 blocks behind head. It uses the same bounded chunking/gap reporting as ERC-20 discovery, checks canonical event blocks and rechecks the range anchor. Events identify candidates; fresh `allowance(owner,token,spender)` calls determine amount, expiration and nonce. No stored grant is inferred merely from ERC-20 approval to Permit2.

Every grant links to an actual `ERC20.allowance(owner,Permit2)` and balance at the same block. Underlying approval is read once per token during a Permit2 run, shared across spender grants. Amount uses uint160 BigInt; expiration and nonce are validated uint48 and converted losslessly to BigInt. Expiration is evaluated against the read block's timestamp using the contract's strict `timestamp > expiration` rule. A zero grant remains zero even if its timestamp is also expired.

The displayed layers overlap: token approval to Permit2 is a prerequisite, not additional independent inventory. Per-spender authority cannot exceed the token balance or underlying allowance; an expired grant has no current AllowanceTransfer authority. No cross-layer amounts are summed or priced as expected loss.

[Official overview](https://developers.uniswap.org/docs/protocols/permit2/overview) and [AllowanceTransfer guide](https://developers.uniswap.org/docs/protocols/permit2/concepts/allowance-transfer) describe the separate permission models. Offchain SignatureTransfer signatures cannot be universally enumerated before execution. Lockdown clears stored amount but does not invalidate every unused signed permit or ordered nonce; the future revocation flow must disclose that residual risk. A new valid signature can recreate authority.
