# Owner-authorized revocation (Module 9)

Open a verified permission's detail page, connect its owner in Settings, and select the inspected chain in the wallet. Prepare revocation runs anonymous preflight without requesting a signature. The confirmation dialog discloses owner, chain, target, token/spender, exact zeroing action, and gas budget. Only a separate Confirm in wallet action requests `eth_sendTransaction`.

Supported actions are narrowly encoded ERC-20 `approve(spender,0)` and canonical Permit2 `lockdown([(token,spender)])`. Arbitrary calldata, transfers, delegated execution and smart-account signing are unsupported. Code-present owners, including delegated-code accounts, remain read-only. No ownership is inferred from inspecting an address.

Before review and again immediately before signing, the engine checks wallet-local authorized accounts/network, anonymous endpoint chain, empty owner bytecode, deployed target code, latest positive allowance, simulation, gas estimate, gas price, native balance and pending nonce. ERC-20 simulation must return a canonical true boolean; false or no-return tokens are unsupported. Permit2 simulation must return empty data. Gas uses a 25% estimate margin, a five-million gas ceiling, and a legacy gas-price transaction compatible with the two supported Ethereum networks. Insufficient ETH blocks submission. Nonces above Number's safe range are rejected because the receipt helper uses numeric nonces. Scope guards reject account, chain, provider, inspection or worker changes. A changed allowance, runtime code, nonce or increased prepared fee budget requires another review. Preparations expire after two minutes.

Target bytecode checks and simulation cannot audit a proxy implementation or guarantee behavior at future inclusion. The wallet's final review remains authoritative for any user-edited fees. No private key or seed is requested or stored.

Receipt tracking uses viem through the same anonymous adapter, with two confirmations, bounded polling and a three-minute timeout. Repricing/replacement is observed where the provider exposes the original transaction; the final mined transaction must retain the exact owner, target, zero value, calldata and nonce. Cancellation or a different replacement action fails verification. If the original transaction disappears before it is observed, universal replacement discovery is unavailable; timeout stays unverified. No indexer or direct fallback is introduced.

Only a successful canonical receipt, matching transaction, at least two block confirmations, and a fresh zero allowance read at/after inclusion produce **Allowance verified zero**. Both the inclusion block and the later state block hashes are rechecked around verification. Preparation also anchors its account/allowance snapshot. Allowance decoding requires canonical ERC-20/Permit2 return words and supported numeric widths. Rejected requests, reverted receipts, nonzero/malformed post-state, worker loss, unknown/dropped transactions, timeouts and reorgs never produce that status. Two confirmations are not Ethereum finality. Verification is timestamped historical evidence; later positive scans remain actionable. Later approvals or signatures can restore authority; stale scan values are explicitly superseded and must be refreshed.

Leaving the permission view cancels final preflight before wallet handoff. Once a request reaches the wallet, navigation cannot retract it; the owner must decide in the wallet, and application receipt tracking continues. No cancellation is presented as proof that a handed-off transaction cannot execute.

Permit2 lockdown clears the selected stored amount. It does not invalidate all unused signed permits, ordered nonces, SignatureTransfer signatures, other spenders, or underlying ERC-20 approval. Removing the underlying approval affects every Permit2 spender for that token and is a separate ERC-20 action. The UI discloses this dependency.

Wallet-provider submission and the wallet's internal RPC traffic are outside Anon-RPC anonymity. Application-controlled preflight, receipt and verification reads stay on the worker. Signing authorization follows [EIP-1193](https://eips.ethereum.org/EIPS/eip-1193). This is application-tested code, not an independent security audit. A configured positive local allowance was subsequently verified, but deliberately preserved. No live signed revocation is claimed: submission awaits the owner's intentional wallet confirmation.
